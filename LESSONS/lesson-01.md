# Занятие 1 — «Как устроена соцсеть» (2 часа)

> Формат: **изучаем готовый код, а не пишем его.**
> Учитель показывает и объясняет, ученики смотрят код и пробуют руками в Swagger.

## Цель занятия

К концу урока каждый ученик:

- понимает, из чего состоит full-stack проект (клиент → сервер → БД);
- умеет запустить бэкенд и открыть Swagger-документацию;
- разбирается в модели данных (таблицы и связи между ними);
- понимает, как работает JWT-авторизация (пароль → хеш → токен → запрос);
- умеет «читать» роутер: endpoint → схема → модель → БД.

## Словарь терминов (ввести в начале, использовать весь урок)

- **Клиент** — то, что видит пользователь (браузер, React-приложение).
- **Сервер** — программа, которая принимает запросы и отдаёт данные (FastAPI).
- **База данных (БД)** — место, где данные хранятся (PostgreSQL).
- **API / endpoint** — конкретный адрес + метод, например `POST /auth/login`.
- **JSON** — текстовый формат обмена данными между клиентом и сервером.
- **Токен (JWT)** — «пропуск», который клиент показывает серверу, чтобы доказать, кто он.

### Шпаргалка понятий (чтобы уверенно объяснять)

- **psql** — консольный клиент PostgreSQL: вводишь SQL-команды и сразу видишь результат.
- **Роль (role) = пользователь БД**. `postgres` — главный (суперпользователь), создаётся при
  установке; его пароль ты задавал тогда же.
- **База данных** — отдельное хранилище со своими таблицами. У нас будет база `unisphere`.
- **OWNER (владелец)** — пользователь, которому база принадлежит и который может в ней всё.
- **Строка подключения** — адрес, по которому приложение находит БД:
  `postgresql+asyncpg://пользователь:пароль@хост:порт/база`.
- **pg_hba.conf** — файл правил «кто и откуда может подключаться». `scram-sha-256` = вход по
  паролю (современный метод); `trust` = без пароля (опасно, только временно).
- **listen_addresses** — на каких интерфейсах Postgres слушает. `*` = на всех, чтобы ученики
  по Wi-Fi могли подключиться.

### A.1 Создать базу и пользователя

> ✅ Уже сделано. Ниже — как это делалось (на случай пересоздания на другом ПК).

Зачем: заводим отдельного пользователя `kiberone` и его базу `unisphere`, чтобы не работать под
суперпользователем `postgres`.

**Шаг 1 — найти psql.** Он лежит в папке установки. Узнай версию:

```powershell
Get-ChildItem "C:\Program Files\PostgreSQL"
```

Увидишь папку с номером (например `16`). Тогда `psql` находится в
`C:\Program Files\PostgreSQL\16\bin\psql.exe`.

**Шаг 2 — подключиться от имени postgres.** В PowerShell (обычном):

```powershell
& "C:\Program Files\PostgreSQL\16\bin\psql.exe" -U postgres -h localhost
```

Появится `Password for user postgres:` — вводишь пароль, заданный при установке Postgres
(символы при вводе не видны, это нормально).

**Шаг 3 — выполнить SQL.** После приглашения `postgres=#` вставь по одной команде:

```sql
CREATE USER kiberone WITH PASSWORD 'kiberpassword';
CREATE DATABASE unisphere OWNER kiberone;
```

Здесь пароль уже вписан — `kiberpassword` (он же используется в строке подключения).

**Шаг 4 — проверить:**

```sql
\du   -- список пользователей: должен появиться kiberone
\l    -- список баз: должна появиться unisphere
```

**Шаг 5 — выйти:**

```sql
\q
```

#### Частые проблемы на A.1

- **«psql не распознан как команда»** — используй полный путь через
  `& "C:\Program Files\...\psql.exe"`.
- **Забыл пароль postgres** — сброс через `pg_hba.conf`: временно поменяй строку
  `host all all 127.0.0.1/32 scram-sha-256` на `trust`, перезапусти службу, зайди и задай новый пароль
  `ALTER USER postgres PASSWORD 'новый_пароль';`, потом верни `scram-sha-256` и снова перезапусти.
- **«Connection refused» на localhost** — служба не запущена: `Get-Service *postgres*`,
  затем `Start-Service postgresql-x64-16`.
- **«role "postgres" does not exist»** — в SQL имя всегда `postgres` (заглавные только в
  названии службы).

### A.2 Разрешить Postgres слушать сеть

> Шаг 1 (`listen_addresses`) ✅ уже сделан. Шаг 2 (`pg_hba.conf`) ❗ ещё нужно сделать.

Зачем: по умолчанию Postgres пускает только с этого же компьютера. Нужно, чтобы ученики
по Wi-Fi тоже могли подключиться.

**Шаг 1** — открой файл `postgresql.conf` (нужны права админа):

```powershell
notepad "C:\Program Files\PostgreSQL\16\data\postgresql.conf"
```

Найди строку `listen_addresses` (может начинаться с `#`). Убери `#` и сделай:

```
listen_addresses = '*'
```

**Шаг 2** — в том же каталоге открой `pg_hba.conf`:

```powershell
notepad "C:\Program Files\PostgreSQL\16\data\pg_hba.conf"
```

В конец файла добавь строку:

```
host  all  all  0.0.0.0/0  scram-sha-256
```

Это разрешает подключаться с любого адреса по паролю. Безопаснее — указать только вашу
подсеть Wi-Fi (например `192.168.0.0/24` вместо `0.0.0.0/0`).

**Шаг 3** — сохрани оба файла. Изменения вступят в силу после перезапуска службы (шаг A.4).

### A.3 Открыть порт в Windows Firewall (от администратора)

> ✅ Уже сделано (правило `PostgreSQL 5432` включено). Ниже — как это делалось.

Зачем: брандмауэр Windows по умолчанию блокирует входящие подключения к порту 5432.
Открой PowerShell **от имени администратора** и выполни:

```powershell
netsh advfirewall firewall add rule name="PostgreSQL 5432" dir=in action=allow protocol=TCP localport=5432
```

### A.4 Перезапустить службу и узнать свой IP

```powershell
Restart-Service postgresql-x64-16
ipconfig
```

В выводе `ipconfig` найди `IPv4-адрес` адаптера Wi-Fi (у тебя сейчас `192.168.0.145`) — это адрес,
который получат ученики.

### A.5 Прогнать миграции ОДИН раз (только учитель!)

### A.6 Проверить связь заранее

С телефона/другого ноутбука в той же сети:

```powershell

```

Должно быть `TcpTestSucceeded : True`. Это проверка, что Wi-Fi не режет связь
«клиент ↔ клиент» (client isolation).

### 1:05–1:25 — Авторизация JWT
- Сначала логика без кода: логин/пароль → сверка хеша → выдача **JWT** → клиент шлёт токен
  в `Authorization: Bearer ...` → сервер по токену понимает, кто это.
- Файлы:
  - `backend/app/core/security.py`:
    - `hash_password` (`:6`) — пароль никогда не храним открытым, только bcrypt-хеш.
    - `verify_password` (`:9`) — сверяем введённый пароль с хешем.
    - `create_access_token` (`:12`) — подписанный токен с `exp` (время жизни).
    - `decode_token` (`:24`) — проверяем подпись и читаем данные.
  - `backend/app/core/deps.py:13` — `get_current_user`: токен из заголовка → декод → поиск
    пользователя; иначе `401`.
  - `backend/app/routers/auth.py`:
    - `register` (`:12`) — проверка занятых email/username → хеш → сохранить.
    - `login` (`:32`) — сверка пароля → `access_token` + `refresh_token`.
    - `me` (`:43`) — «кто я?» по токену.
  - Схемы `backend/app/schemas/schemas.py`: `RegisterRequest` (`:6`), `LoginRequest` (`:11`),
    `TokenResponse` (`:15`), `UserOut` (`:20` — в ответе **нет** `password_hash`).
- Где путаются:
  - `password` (вводит пользователь) ≠ `password_hash` (хранится в БД).
  - `access_token` (короткий, для запросов) vs `refresh_token` (долгий, для обновления).
  - `async/await` и `Depends` — пока упрощённо: «FastAPI сам подставляет зависимости».

## Часть F. Мини-квиз (с ответами для учителя)

1. **Где хранятся пароли и почему их не видно в ответе API?**
   В БД лежит только bcrypt-хеш (`password_hash`), а схема `UserOut` не содержит это поле —
   поэтому в JSON пароль/хеш не попадает.

2. **Что произойдёт, если вызвать `/auth/me` без токена, и почему?**
   Ответ `401 Unauthorized`: `get_current_user` (`deps.py:13`) не найдёт токен → поднимет исключение.

3. **Чем `Post.author` (relationship) отличается от `Post.author_id` (колонка)?**
   `author_id` — реальная колонка с внешним ключом в БД; `author` — ссылка на объект `User` в Python,
   которую SQLAlchemy заполняет автоматически.

4. **Что такое UUID и зачем его использовать вместо автоинкремента 1, 2, 3?**
   Глобально уникальный идентификатор; не раскрывает порядок/количество записей, удобно при
   распределённой системе (несколько серверов не конфликтуют за id).

5. **Зачем нужен файл `.env`?**
   Хранить конфигурацию и секреты (пароль БД, `SECRET_KEY`) вне кода, чтобы не коммитить их в git.
